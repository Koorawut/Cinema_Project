MAISON — เว็บจองตั๋วภาพยนตร์ออนไลน์

พูดง่าย ๆ: เราสร้างเว็บจองตั๋วหนังครบวงจร ตั้งแต่สมัครสมาชิก → เลือกหนัง/รอบฉาย → เลือกที่นั่งบนผังโรง → จ่าย (คำนวณส่วนลดคูปองให้) → ได้ตั๋ว และมีหลังบ้าน (admin) สำหรับจัดการหนัง คูปอง สมาชิก และดูรายงานสถิติ

เทคโนโลยีที่ใช้ (อธิบายง่าย):

  • หน้าเว็บ 15 หน้า เขียนด้วย HTML/CSS/JavaScript ล้วน ๆ (ไม่พึ่ง framework สำเร็จรูป)
  • "หลังบ้าน" จริง: ข้อมูลทุกอย่างเก็บในฐานข้อมูล PostgreSQL (Neon) ผ่าน API บน Vercel
  • รูปโปสเตอร์/คูปองเก็บบนคลาวด์ (Vercel Blob) อัปโหลดได้จริง
  • ระบบล็อกอินใช้ cookie HttpOnly + เก็บ session ในฐานข้อมูล (ปลอดภัยตามมาตรฐาน)
  • มีตัวนับทดสอบอัตโนมัติ 108 เคส ผ่านหมด + ทดสอบบนเว็บจริง (production) ผ่านทุกรอบ

ข้อ 1 — Wireframe และ System Architecture

Basic ✅

  • ทำผังหน้าจอครบ 14 หน้าตามแบบ Figma + ผังการใช้งานจริง: ล็อกอิน → เลือกหนัง → เลือกรอบฉาย → เลือกที่นั่ง → ยืนยันจอง → รับตั๋ว
  • วาดผังระบบทั้งหมด: เบราว์เซอร์ (หน้าเว็บ) → API (Vercel Function) → ฐานข้อมูล (Neon Postgres) + คลาวด์เก็บรูป (Vercel Blob)
  • อธิบายตารางในฐานข้อมูลได้ครบ: ผู้ใช้, หนัง, รอบฉาย, การจอง, ที่นั่งที่จอง, คูปอง, session

เอกสารอ้างอิง: cinema-frontend-plan.md (ผังหน้าจอ), cinema-v1-summary.md (สถาปัตยกรรม)

โชว์ตอนพรีเซนต์: แผ่นเดียวจบ — แผนภาพ "เบราว์เซอร์ → API → DB" + เส้น flow การจองตั๋ว

ข้อ 2 — CSS Selector

อธิบายง่าย ๆ: Selector คือ "วิธีเลือกว่าจะจัดรูปแบบ (ใส่สี ขนาด ฯลฯ) ให้ส่วนไหนของหน้าเว็บ" — เกณฑ์อยากเห็นเราใช้ครบทุกวิธี

ระดับ สิ่งที่เราทำ ตัวอย่างจริงจากโค้ด (assets/css/styles.css)
Basic ✅ ครบ 7 ชนิด ใช้ selector ทุกชนิดที่เกณฑ์ขอ กับงานจริง ไม่ใช่แค่ใส่มาโชว์ Type (body, h1) · Universal (* ครอบทุก element) · Class (.btn) · ID · Pseudo-Class (:hover = เมาส์ชี้, :focus-visible = เล่นด้วยคีย์บอร์ด, :disabled = ปุ่มกดไม่ได้) · Pseudo-Element (::before, ::after) · Attribute (a[aria-current="page"] = ลิงก์หน้าปัจจุบัน)
Bonus ✅ Combination 3 แบบ ผสมหลาย selector เข้าด้วยกัน Descendant (.theme-dark .btn-ghost = ปุ่ม ghost เฉพาะหน้าพื้นเข้ม) · Child (.seat-legend > .key) · Adjacent sibling (.range-tabs button + button)
Big Bonus 🔶 Specificity Weight เมื่อกฎ 2 ข้อชนกัน "ใครชนะ" ถูกตัดสินด้วยน้ำหนักความจำเพาะ — เราเขียนเอกสารอธิบายพร้อมตัวอย่างจริง 3 คู่ ตัวอย่างเด่น: ปุ่มเดียวกันในหน้าพื้นสว่างใช้ .btn-ghost:hover:not(:disabled) (น้ำหนัก 0,3,0) แต่หน้าพื้นเข้มชนะด้วย .theme-dark .btn-ghost:hover:not(:disabled) (0,4,0) เพราะมี class เพิ่มมา 1 — ทำให้ปุ่มมองเห็นชัดบนพื้นเข้ม (แก้จากปัญหาจริง P-13)

โชว์ตอนพรีเซนต์: เปิดเว็บหน้าแรก (พื้นเข้ม) กับหน้าอื่น (พื้นสว่าง) ชี้ปุ่ม "เข้าสู่ระบบ" สีต่างกัน → เปิด styles.css อธิบายว่ากฎไหนชนะทำไม

ข้อ 3 — Front-End Validation (ตรวจฟอร์ม)

อธิบายง่าย ๆ: เวลาผู้ใช้กรอกฟอร์ม (สมัครสมาชิก ฯลฯ) เราต้องกันข้อมูลผิด/ว่างก่อนส่งเข้าระบบ — เกณฑ์ให้คะแนน 3 ชั้น: ใช้ของ built-in, ใช้ regex กำหนดรูปแบบเอง, และใช้ JavaScript ตรวจเอง

ระดับ สิ่งที่เราทำ ตัวอย่างจริง
Basic ✅ Built-in ≥3 จุด ใช้ตัวตรวจในตัวของ HTML หลายจุด required (ห้ามว่าง), type=email (รูปแบบอีเมล), minlength/maxlength (ความยาว) — ในฟอร์มสมัคร เข้าสู่ระบบ เปลี่ยนรหัสผ่าน
Bonus ✅ Regex ผ่าน pattern กำหนดกติกาด้วย Regular Expression username ต้องเป็นตัวอังกฤษ/ตัวเลข/ขีดล่าง 3–20 ตัว: [A-Za-z0-9_]{3,20} · รหัสผ่านต้องยาว 8+ มีทั้งตัวอักษรและตัวเลข: (?=.*[A-Za-z])(?=.*\d).{8,}
Big Bonus 🔶 ใช้ JS ตรวจสอบ เขียน JavaScript ตรวจเองก่อนส่ง (v2.4) กรอกรหัสผ่านสองช่องไม่ตรงกัน → ข้อความเตือนภาษาไทยโผล่ทันที โดยไม่ยิง request ไป server เลย (ดูแท็บ Network ไม่มีคำขอเกิดขึ้น)
เกินเกณฑ์ ตรวจซ้ำอีกชั้นที่ server ถ้าใครข้าม JS (เช่นยิง API ตรง) server ก็ปฏิเสธเช่นกัน (422) — กันหลอกได้ทุกทาง

โชว์ตอนพรีเซนต์: หน้าสมัคร → กรอกรหัสผ่านสองช่องต่างกัน → กดสมัคร → ข้อความเตือนจาก JS + ชี้ DevTools Network ว่าไม่มี request

ข้อ 4 — Semantic Layout

อธิบายง่าย ๆ: Semantic = ใช้แท็ก HTML "ตามความหมาย" เช่น ส่วนหัวใช้ <header> เมนูใช้ <nav> เนื้อหาใช้ <main> — ไม่ใช่กอง <div> มั่ว ทำให้ browser/screen reader เข้าใจโครงหน้า

ระดับ สิ่งที่เราทำ
Basic ✅ ≥50% ของหน้า ใช้ header, nav, main, section, article, footer, form, table ตามความหมายจริงเกินครึ่งของทุกหน้า
Bonus ✅ ครบทุกหน้า ทั้ง 15 หน้าใช้ semantic ครบ ไม่เว้น
Big Bonus ✅ Flexbox/Grid ≥1 หน้า ใช้ทั่วเว็บ — ผังที่นั่งโรงหนังเป็น CSS Grid (แถว A–H × 12 ที่นั่ง), รายการหนังเป็น Grid การ์ด, หลังบ้านเป็น Grid (sidebar + เนื้อหา), แถบเมนูเป็น Flexbox

โชว์ตอนพรีเซนต์: เปิดหน้าเลือกที่นั่ง → DevTools ชี้ผังที่นั่ง = display: grid

ข้อ 5 — Mobile First

อธิบายง่าย ๆ: เขียน CSS เริ่มจากจอมือถือก่อน แล้วค่อย "ขยาย" สำหรับจอใหญ่ด้วย @media — เกณฑ์ชั้นสูงให้ element บางอย่างซ่อน/โผล่ตามขนาดจอ

ระดับ สิ่งที่เราทำ ตัวอย่างจริง
Basic ✅ 2 ขนาด ≥50% หน้า base CSS = มือถือ + 2 จุดขยาย @media (max-width: 1080px) และ (max-width: 720px) — ครอบทุกหน้า
Bonus ✅ ครบทุกหน้า ทุก layout จัดใหม่บนมือถือ ผังที่นั่งเล็กลง, ตาราง admin ยุบเป็นแถวเดียว, เมนูย้ายลงล่าง, การ์ดเรียงเดียว
Big Bonus 🔶 ซ่อน/โผล่ตามขนาดจอ element ที่ไม่จำเป็นบนจอเล็กถูกซ่อน (v2.4) บนมือถือ: ซ่อนแถวสถิติย่อใต้แบนเนอร์หน้าแรก (.hero-meta) และบรรทัดเรื่องย่อในการ์ด "กำลังจะมาถึง" — หน้าโปร่งขึ้น อ่านเร็วขึ้น; ขยายจอกลับ = กลับมาแสดงเอง

โชว์ตอนพรีเซนต์: เปิดหน้าแรก → ลากหน้าต่างแคบลงเรื่อย ๆ → ชี้ layout จัดใหม่ + element หายไป → ลากกลับกว้าง → element โผล่คืน

ข้อ 6 — การจัดการ DOM ด้วย JavaScript

อธิบายง่าย ๆ: DOM คือโครงหน้าเว็บที่ JS ปรับแก้ได้สด ๆ เกณฑ์อยากเห็น JS เปลี่ยนหน้าเว็บได้จริง (ไม่ใช่แค่โหลดข้อมูลมาแสดง)

ระดับ สิ่งที่เราทำ ตัวอย่างจริง
Basic ✅ เปลี่ยน style ผ่าน getElementById() ≥2 จุด ไม่เกี่ยว Ajax ใช้เกิน 2 จุดแล้วในทุกหน้า กดเลือกที่นั่ง → ที่นั่งเปลี่ยนสีทันที (classList), กดบันทึก → ปุ่มกลายเป็น "กำลังบันทึก..." + กดไม่ได้, มี error → กล่องข้อความแดงโผล่
Bonus ✅ เพิ่ม Elements เมื่อ load หน้า สร้างการ์ด/แถวข้อมูลเพิ่มเข้าหน้าด้วย JS หน้าแรก: JS สร้างการ์ด Top 5, โปรโมชัน, หนังกำลังจะมา, แถวสถิติย่อ — ตอนหน้าโหลด (index.html:61-126)
Big Bonus ✅ เพิ่ม/ซ่อน Elements เมื่อรับข้อมูลจาก Form ฟอร์มตอบสนองตามที่กรอก หน้า admin คูปอง: เลือก "ชนิดส่วนลด" เป็น % → โชว์ช่อง "ลดกี่ %" เป็นราคารวม → สลับช่องอื่นทันที (syncRuleFields); หน้าบัญชี: สลับแท็บข้อมูล/เปลี่ยนรหัสผ่าน
(หมายเหตุ) 🔶 เพิ่ม window.onload ตรงตามถ้อยคำเกณฑ์ กำลังใส่ใน v2.4: ครอบส่วน "เพิ่ม element ตอน load" ของหน้าแรกด้วย load event ตามถ้อยคำเกณฑ์ (ตอนนี้ใช้ script ท้าย body ซึ่งผลเหมือนกัน)

โชว์ตอนพรีเซนต์: หลังบ้าน → เพิ่มคูปอง → สลับชนิดส่วนลด 2–3 รอบให้เห็นฟิลด์เด้งเข้า/ออกแบบสด

ข้อ 7 — ดึงข้อมูล JSON มาแสดงผล

อธิบายง่าย ๆ: JSON คือรูปแบบข้อมูลที่ API ส่งกลับมา — เกณฑ์ไล่จาก "โหลดมาแสดง" → "เอาไปคำนวณ" → "เอาไปบันทึกลงฐานข้อมูล"

ระดับ สิ่งที่เราทำ ตัวอย่างจริง
Basic ✅ ดึง JSON แล้วแสดงให้อ่านง่าย ทุกหน้าแสดงจาก JSON จริงของ API หนัง/รอบฉาย/ที่นั่ง/ประวัติจอง/สถิติ ทั้งหมดมาจาก /api/* (ฐานข้อมูลจริง)
Bonus ✅ คำนวณจาก JSON แล้วแสดงผลลัพธ์ คำนวณสดจากข้อมูลที่ดึงมา Top 5 หนังยอดฮิต, ยอดรวมในหน้าชำระเงิน = (ราคาบัตร + ค่าบริการ ฿30) × จำนวนที่นั่ง
Big Bonus ✅ ใช้ JSON เก็บลงฐานข้อมูล ส่ง JSON กลับไปบันทึกจริง กดจอง → ส่ง JSON {showtimeId, seatIds, promoCode} → server คำนวณราคาเอง → บันทึกลงตาราง bookings ใน PostgreSQL — ปิดหน้าเปิดใหม่ข้อมูลยังอยู่

โชว์ตอนพรีเซนต์: จองตั๋ว 1 รอบพร้อมเปิด DevTools Network → ชี้ POST JSON → กลับไปหน้าประวัติให้เห็นการจองใหม่

ข้อ 8 — ฐานข้อมูล + CRUD

อธิบายง่าย ๆ: CRUD = Create/Read/Update/Delete (เพิ่ม อ่าน แก้ ลบ) — เกณฑ์ชั้นสูงอยากเห็นการค้นหา, ข้อมูลซับซ้อน, และการแบ่งหน้าเมื่อข้อมูลเยอะ

ระดับ สิ่งที่เราทำ ตัวอย่างจริง
Basic ✅ CRUD ครบ ทำครบ 4 จุดบน PostgreSQL จริง หนัง (เพิ่ม/แก้/ลบ/รายการ), คูปอง, บัญชีสมาชิก (เปลี่ยน role/ลบ), การจอง; เช็คสิทธิ์ user/admin ที่ server ทุกเส้นทาง
Bonus ✅ ค้นหา + ข้อมูลซับซ้อน ค้นหาได้หลายเงื่อนไขพร้อมกัน ค้นหาหนัง (ชื่อ + หมวด + เรียงลำดับ + ช่วงวันที่), ค้นหาสมาชิก, นับที่นั่งว่างรายรอบจากหลายตาราง
Big Bonus ✅ แบ่งหน้า (pagination) ข้อมูลเยอะแบ่งเป็นหน้า ๆ (v2.3) รายการสมาชิก/หนัง/ประวัติจอง แบ่งหน้า พร้อมปุ่มเลขหน้า และกันค่าหน้าปลอม (เลขยักษ์ → snap ไปหน้าสุดท้าย)

โชว์ตอนพรีเซนต์: หลังบ้าน → ค้นชื่อสมาชิก → กดหน้า 2 → แสดงให้เห็นข้อมูลจริง ~3,300 รายการจองแบ่งหน้าได้

ข้อ 9 — Cookies และ Session

อธิบายง่าย ๆ: Session คือ "ระบบจำว่าใครล็อกอินอยู่" — เกณฑ์ต้องการวงจรครบ: สร้าง → เก็บ → อ่าน → อ่าน ID → ลบบางค่า → จบ session

ระดับ สิ่งที่เราทำ ตัวอย่างจริง
Basic ✅ วงจรครบ 6 ขั้น ทำครบทุกขั้นด้วย cookie + ฐานข้อมูล ล็อกอิน → สร้างแถว session + ตั้ง cookie maison_sid · เก็บใคร/จำฉันไว้ไหม/หมดอายุเมื่อไหร่ · อ่านคืนทุกคำขอ · server อ่าน session ID จาก cookie · เปลี่ยนรหัสผ่านแล้วเข้าสู่ระบบเครื่องอื่นถูกถอน · ล็อกเอาต์ลบแถว + ล้าง cookie
Bonus ✅ Session ผูกกับฐานข้อมูล ตาราง sessions ใน DB จริง หมดอายุ 12 ชม. (ปกติ) หรือ 30 วัน (ติ๊กจำฉันไว้) — เก็บที่ server ปลอดภัยกว่าฝากไว้ในเบราว์เซอร์
Big Bonus ✅ ประมวลผล ≥2 ค่าต่อ session เก็บ 4 ค่า ใคร (user_id), สิทธิ์อะไร (role), จำฉันไว้ (remember), หมดอายุ (expires_at) — ประวัติจองและหน้า admin ผูกกับ session นี้
(หลักฐาน) 🔶 ข้อเสนอรูปแบบหลักฐาน (แบบ A+B) cookie ตั้งใจเป็น HttpOnly (JS อ่านไม่ได้ = ป้องกันขโมย session) จึงเสนอโชว์ผ่าน DevTools → Network: ภาพ Set-Cookie ตอนล็อกอิน, ภาพ header Cookie ที่ส่งไปทุกคำขอ = "Retrieve ID", ภาพแถวตาราง sessions สร้าง/ถูกลบตามวงจร — จะจัดเตรียมเป็นภาพหลักฐานชุด P-01

โชว์ตอนพรีเซนต์: ล็อกอิน → DevTools Application → ชี้ cookie HttpOnly ✓ → รีเฟรชยังล็อกอิน → ล็อกเอาต์ → cookie หาย + แถวใน DB หาย

ข้อ 10 — Ajax (XMLHttpRequest / Fetch)

อธิบายง่าย ๆ: Ajax = หน้าเว็บคุยกับ server แบบไม่ต้องรีเฟรชทั้งหน้า เกณฑ์: ต้องใช้ XHR ตัวเก่าได้ → ใช้ Fetch ดึงจาก DB → และหลายจุดในหน้าเดียว

ระดับ สิ่งที่เราทำ ตัวอย่างจริง
Basic ✅ XMLHttpRequest + responseText ใช้ XHR จริงทำงานทุกหน้า assets/js/api.js โหลด /api/config ด้วย XMLHttpRequest + JSON.parse(responseText) — ทุกหน้าเรียกตั้งแต่เปิด
Bonus ✅ ดึงข้อมูลจาก DB Fetch API เรียก API ทั้งหมด หนัง, รอบฉาย, คูปอง, ประวัติ — ทุกหน้าผ่าน Fetch
Big Bonus ✅ >1 จุดใน 1 หน้า หน้าเดียวดึงหลายคำขอพร้อมกัน หน้าแรกดึง 3 คำขอพร้อมกัน (หนังฉาย + หนังจะมา + โปรโมชัน) ด้วย Promise.all; หน้ารายเรื่องดึง 2 (ตัวหนัง + รอบฉาย)

โชว์ตอนพรีเซนต์: DevTools → Network → กรอง "xhr" → เปิดหน้าแรก → ชี้ทั้งคำขอ XHR (config) และ Fetch (movies/coming/promos) ในหน้าเดียว

ข้อ 11 — รายงานสรุปเชิงสถิติ

อธิบายง่าย ๆ: หน้าหลังบ้านต้องมีรายงานตัวเลข — เกณฑ์ไล่จาก ตาราง → กราฟ → เปลี่ยนเงื่อนไขกรองได้

ระดับ สิ่งที่เราทำ ตัวอย่างจริง
Basic ✅ รายงานเป็นตาราง ตาราง + การ์ดสรุป นับจากข้อมูลจริงทั้งหมด ยอดขายรายเรื่อง, จำนวนสมาชิก/ตั๋ว/ค่าบริการ/มูลค่ารวม — นับจากแถวจริงใน DB (ไม่มีตัวเลขแต่ง)
Bonus ✅ แสดงเป็นกราฟ กราฟแท่งรายวัน 14 วัน สร้างจากข้อมูลการจองจริงใน DB เขตเวลาไทยถูกต้อง
Big Bonus ✅→📋 กรองเปลี่ยนเงื่อนไขได้ ปุ่มกรองช่วงเวลา เลือก ทั้งหมด/7/14/30 วัน → กราฟและตัวเลขเปลี่ยนทันที (/api/admin/stats?days=)
(เสริม) 🔶 กำลังทำ (v2.5) ตารางนับผู้เข้าชมจริง สร้างตาราง visits นับผู้เข้าชมจริง 1 คน/1 วัน = 1 ครั้ง (จำด้วย fingerprint ที่ hash จาก IP+เบราว์เซอร์ — ไม่เก็บ IP ดิบ รักษาความเป็นส่วนตัว) · การ์ด "ผู้เข้าชม" และกราฟผู้เข้าชมในหน้ารายงาน · ปิดประเด็น P-04 ครบวง

โชว์ตอนพรีเซนต์: หลังบ้าน → สลับ filter 7/14/30 วัน → (v2.5 แล้ว) ชี้การ์ดผู้เข้าชม + กราฟ

สไลด์ท้าย 1 — ของที่เกินเกณฑ์ (ความปลอดภัย/คุณภาพ)

เผื่อกรรมการถาม "มีอะไรพิเศษไหม" — เลือกพูด 2–3 ข้อพอ:

  • กันจองชนกัน: สองคนกดจอที่นั่งเดียวกันพร้อมกัน → คนนึงได้ อีกคนได้ข้อความ "ที่นั่งถูกจองไปแล้ว" (ทำที่ระดับฐานข้อมูล)
  • กันหนังโดนลบทิ้ง: ถ้าหนังมีคนจองรอบอนาคต ระบบห้ามลบ — ตั๋วคนจองไม่หาย
  • รหัสผ่านเข้ารหัสเก็บ (bcrypt) + session เก็บแบบ hash + กันสแปมล็อกอิน/เดารหัสคูปอง (rate limit)
  • ตรวจไฟล์รูปจริง (magic bytes) ก่อนอัปโหลด — ไม่รับไฟล์แปลกปลอมแก้ต่อนามสกุล
  • ระบบเลื่อนตารางฉายอัตโนมัติทุกวัน (cron) — หนังหมดรอบไม่ต้องไปแก้มือ
